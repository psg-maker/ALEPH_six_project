# ALEPH — 로그인으로 내 계획과 실행을 보호하는 앱

7번 과제의 구조와 설계, 그리고 혼자 쓰는 프로그램을 여러 사람이 사용하는 서비스로 발전시키는 과정을 기록합니다. 어려운 기술을 한꺼번에 도입하기보다, 기존 코드를 이해하면서 필요한 구조를 하나씩 추가하는 것이 목표입니다.

**현재 상태: 가입·로그인·현재 사용자 확인·로그아웃·비밀번호 변경 API를 임시 DB에서 검증했습니다. 기존 자료 API의 인증/소유권 검사·실제 자료 이전·5일 비교 기능은 아직 구현하지 않았습니다.**

학습 진행: User 모델, app/security.py의 비밀번호 해시 함수, UserCreate/UserRead, 인증 입력 오류 처리기와 POST /auth/register를 작성했습니다. pwdlib 0.3.1을 requirements.txt에 기록했습니다. 가입 성공·중복 아이디 거절·원문 없는 오류·같은 비밀번호의 서로 다른 Argon2id 해시·공개 필드만 포함한 응답을 임시 DB에서 검증했습니다. 로그인 정보 확인용 authenticate_user도 독립 함수로 정의하고 정상/실패 동작을 검사했습니다. 가입·로그인 HTTP API는 로컬 검증 단계이며 배포 적용은 아직 하지 않았습니다.

## 1. 문서와 과제의 구분

세션 학습 진행: AuthSession 모델·무작위 세션 값 생성·SHA-256 변환·12시간 세션 저장을 로그인 API와 쿠키 발급에 연결했습니다. GET /auth/me는 세션의 만료·폐기를 검사합니다. 로그아웃은 현재 세션, 비밀번호 변경은 본인 기존 세션 전체를 폐기합니다. 새 비밀번호 재로그인과 DB 저장 실패 시 해시/세션의 동시 rollback도 확인했습니다. 최신 전체 Python 테스트는 31개 통과입니다. 실제 브라우저·배포 검증과 기존 자료 API의 인증/소유권 검사·자료 이전은 아직 남아 있습니다.

## 3. 이해하기 쉬운 인증 구조 — 제안

### 선택한 방향과 이유

**기존 FastAPI에 아이디·비밀번호 가입과 DB 세션 인증을 구현하고, 비밀번호 처리는 `pwdlib`의 Argon2 지원에 맡기는 방향을 제안합니다.** 사용자 이해 난도를 낮춰 달라는 요청에 맞춘 Codex의 설계 제안이며, 구현을 마친 사실이나 세부 정책에 대한 사용자 승인으로 기록하지 않습니다.

- 아이디로 가입하므로 처음부터 이메일 발송·이메일 인증 서비스를 연결할 필요가 없습니다.
- 지금 쓰는 FastAPI·SQLAlchemy·Neon 구조를 유지합니다.
- 로그인 상태를 DB에서 확인하므로 로그아웃 때 어떤 값을 끊는지 설명하기 쉽습니다.
- 비밀번호 해시 알고리즘과 salt 처리는 라이브러리를 사용합니다. FastAPI 공식 안내도 `pwdlib`과 Argon2 사용 예제를 제공합니다. [공식 안내](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/)

인증 방식의 정확한 표기는 **“가입·세션 흐름 직접 구현 + 비밀번호 해시 라이브러리 사용”**입니다. 인증 전체를 외부 서비스나 완성된 인증 라이브러리에 맡긴 것으로 설명하지 않습니다. 실제 설치 버전은 구현 때 확인한 뒤 기록합니다.

| 비교한 방법 | 이번에 우선 선택하지 않은 이유 |
| --- | --- |
| 외부 인증 서비스 | 외부 계정·설정과 자료 소유권 연결까지 한 번에 배워야 함 |
| JWT를 발급하고 브라우저에서만 삭제 | 서버가 이전 값을 거절하게 만드는 별도 폐기 설계가 필요함 |
| 비밀번호 해시를 직접 제작 | 검증된 구현을 사용하고 앱의 흐름과 소유권 검사에 집중하기로 함 |

JWT도 서버에서 폐기 여부를 검사하도록 설계할 수 있습니다. 이번 선택은 가능한 방법 중 현재 앱과 학습 목적에 맞춘 것입니다.

### 용어를 앱 동작으로 이해하기

| 용어 | 이 앱에서 뜻하는 것 |
| --- | --- |
| 인증 | 지금 요청한 사람이 누구인지 확인 |
| 인가 | 그 사람이 요청한 자료를 다뤄도 되는지 확인 |
| 비밀번호 해시 | 비밀번호 원문 대신 저장하는 검사용 값 |
| salt | 같은 비밀번호도 서로 다른 해시가 되도록 사용하는 무작위 값. 라이브러리가 처리 |
| 세션 | 로그인 후 서버가 보관하는 유효기간이 있는 로그인 기록 |
| 쿠키 | 브라우저가 같은 서버에 요청할 때 함께 보내는 작은 값 |
| 소유자 ID | 자료가 어느 사용자에게 속하는지 나타내는 DB 값 |

### 제안 구조

```text
브라우저의 로그인 화면
    │ 아이디·비밀번호 전송(배포 환경은 HTTPS)
    ▼
FastAPI ── pwdlib로 비밀번호 확인
    │ 성공하면 무작위 세션 값 발급
    ├─ 브라우저: HttpOnly 쿠키에 세션 값 보관
    └─ DB: 세션 값의 해시·사용자 ID·만료 시각 보관

이후 자료 요청
    → 서버가 쿠키 값의 해시로 세션 조회
    → 만료·폐기 여부 확인
    → 사용자 ID 확인
    → 그 사용자가 소유한 자료만 조회·변경
```

서버 메모리의 Python 사전 대신 DB에 세션을 둡니다. 요청을 처리하는 서버 인스턴스가 달라져도 같은 로그인 상태를 확인할 수 있도록 하기 위한 설계입니다.

### 요청별 처리 순서

**가입**

1. 아이디와 비밀번호의 입력 형식을 검사합니다.
2. 아이디를 정한 규칙으로 정규화합니다. 중복은 서버 검사뿐 아니라 DB 고유 조건으로도 막습니다.
3. 라이브러리가 만든 비밀번호 해시만 저장합니다. 원문은 로그·응답·문서에 남기지 않습니다.
4. 중복 아이디에는 정해진 오류를 반환합니다.

**로그인**

1. 아이디로 사용자를 찾고 라이브러리로 비밀번호를 검사합니다.
2. 없는 아이디와 틀린 비밀번호는 같은 실패 문구를 반환합니다.
3. 성공하면 추측하기 어려운 세션 값을 새로 만듭니다.
4. DB에 세션 값의 해시와 만료 시각을 저장하고, 브라우저에 쿠키를 설정합니다.

**자료 요청**

1. 세션이 없거나 만료·폐기됐으면 API는 401로 거절합니다.
2. 로그인한 사용자 ID를 서버가 결정합니다. 요청 본문·URL·헤더의 다른 사용자 ID를 신뢰하지 않습니다.
3. 자료 ID와 소유자 조건을 함께 검사합니다.
4. 다른 사람 자료와 없는 자료는 동일하게 404로 처리하는 정책을 제안합니다.
5. 소유권 확인 후에만 변경하고, 실패하면 트랜잭션 전체를 취소합니다.

**로그아웃·비밀번호 변경**

- 로그아웃은 현재 세션을 DB에서 폐기하고 쿠키도 지웁니다.
- 비밀번호 변경은 현재 비밀번호 확인 후 새 해시를 저장하고, 해당 사용자의 기존 세션을 모두 폐기하는 방향을 제안합니다. 이후 다시 로그인합니다.
- 이전 쿠키를 보관했다가 다시 보내도 서버가 거절해야 합니다. OWASP는 로그아웃과 만료 때 서버 측 세션 무효화를 요구합니다. [세션 관리 안내](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

쿠키에는 `HttpOnly`, 배포 환경의 `Secure`, 적절한 `SameSite`를 설정하고 변경 요청에는 CSRF 방어를 둡니다. `SameSite`만으로 모든 변경 요청을 보호했다고 보지 않습니다. [쿠키·세션 설정](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [CSRF 방어](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

아이디 정규화·입력 길이·세션 유효기간·CSRF 처리의 구체적인 정책은 구현 설계에서 확정하고 여기에 갱신합니다.

## 4. DB에서 사용자별 자료를 구분하는 방법 — 제안

| 대상 | 변경 방향 |
| --- | --- |
| User | 사용자 ID·정규화한 고유 아이디·비밀번호 해시·생성 시각 |
| AuthSession | 사용자 참조·고유 세션 해시·만료/폐기 시각 |
| Plan | user_id 모델 정의·임시 DB 검증 완료. 실제 DB 컬럼 추가·기존 자료 연결은 예정 |
| Task | 연결된 Plan의 소유자를 통해 접근 검사 |
| Execution·TaskLink | 연결된 Task → Plan의 소유자를 통해 접근 검사 |
| PlanVersion·Review | 연결된 Plan의 소유자를 통해 접근 검사 |
| Review.next_plan_id | 현재 계획과 연결 대상 계획 모두 같은 사용자의 소유인지 검사 |
| DailyNote | user_id와 `(사용자 ID, 날짜)` 고유 조건의 모델 정의·임시 DB 검증 완료. 실제 DB 적용은 예정 |

예를 들어 사용자 A와 B가 같은 날짜에 일일 메모를 작성해도 각각 저장돼야 합니다. 현재 날짜만 고유한 구조를 그대로 두면 다중 사용자 기능과 맞지 않습니다.

현재 모델의 메모 고유 조건은 사용자·날짜 조합입니다. 같은 사용자·날짜에 새 행을 추가하는 것은 거절하고, 기존 행의 content 수정은 허용합니다. 서로 다른 사용자의 같은 날짜 저장과 기존 메모 수정 시 ID/행 수/다른 사용자 자료 보존을 검증했습니다. 이 단계까지 전체 Python 테스트는 34개 통과했으며 실제 DB 스키마 변경은 아직 수행하지 않았습니다.

목록·검색·필터·집계·근거 목록·내보내기도 사용자 범위를 적용합니다. 개별 ID 조회만 막고 목록에 다른 사람 자료가 섞이는 경우도 검사합니다.

내보내기에는 사용자 자신의 앱 자료만 담고 비밀번호 해시·세션 해시·쿠키 값은 포함하지 않습니다. 7번용 DB 계약을 작성할 때 기존 6번 계약의 설명과 구분합니다.

## 5. 기존 6번 자료를 안전하게 이전하는 순서

```text
기존 DB와 제출 커밋 확인
→ 백업과 기존 ID·값·관계 점검
→ 테스트 DB에서 사용자·소유권 스키마 변경 리허설
→ 자료를 받을 본인 계정 지정
→ 지정한 계정에 기존 자료 연결
→ 이전 전후 ID·값·관계·건수 대조
→ 인증을 포함한 앱과 DB 변경을 맞춰 배포
→ 본인 계정 조회 및 다른 계정 접근 거절 확인
```

“처음 가입한 사람”에게 기존 자료를 자동으로 주지 않습니다. 공개 가입 순서가 자료 소유자를 결정해서는 안 됩니다. 소유자 지정 방법은 실제 계정 생성 전에 정합니다.

기존 ID·실행 내용·계획 수정 이력을 보존합니다. 기존 DB에 `create_all()`만 실행해도 컬럼·고유 조건이 바뀌는 것은 아니므로, 별도 마이그레이션이 필요합니다. 배포 순서와 실패 시 복구 방법까지 테스트한 뒤 적용합니다.

## 6. 개인 프로그램에서 다중 사용자 서비스로 발전시키는 판단 순서

먼저 다음 질문을 차례로 확인합니다. 서비스가 커졌다는 이유만으로 모든 기술을 한꺼번에 추가하지 않습니다.

```text
1. 내 PC 밖에서도 써야 하나?
   → 서버에 배포하고 영구 저장 위치를 정한다.
2. 여러 사람이 서로 다른 자료를 쓰나?
   → 사용자·인증·자료 소유권·접근 제한을 추가한다.
3. DB 구조를 바꾸면서 기존 자료를 유지해야 하나?
   → 백업·마이그레이션·복구 절차를 둔다.
4. 무엇이 느리거나 실패하는지 측정했나?
   → 로그·응답 시간·DB 쿼리와 연결 수부터 확인한다.
5. 확인한 원인은 무엇인가?
   → 원인에 맞는 인덱스·캐시·작업 큐·서버 확장을 선택한다.
6. 바꾼 뒤 개선됐고 사용자 자료가 분리되는가?
   → 같은 기준으로 다시 측정하고 권한 검사도 반복한다.
```

| 상황·문제 | 보통 고려하는 구성 | 이 프로젝트에서의 판단 |
| --- | --- | --- |
| 혼자 로컬에서 기능을 익힘 | Python·FastAPI·SQLite | 6번 로컬 개발 구성으로 사용 중 |
| 외부 기기에서도 접속·저장 | 호스팅·HTTPS·영구 DB | Vercel·Neon 사용 중 |
| 여러 사용자가 각자 자료 사용 | User·비밀번호 라이브러리·세션·소유권 검사 | 7번의 우선 구현 대상 |
| 기존 자료를 유지한 DB 변경 | SQL 마이그레이션 스크립트 또는 Alembic | 이번 스키마 변경부터 이전/복구 절차 필요. 도구는 설계 때 선택 |
| 자주 조회하는 목록이 느림 | 쿼리 개선·소유자/날짜 인덱스·페이지 나누기 | 실제 쿼리와 응답 시간을 확인한 뒤 적용 |
| 같은 계산을 반복해 DB 부담 증가 | 캐시. 공유 캐시가 필요하면 Redis 등 검토 | 현재 필수 도입 대상 아님. 캐시 키에도 사용자 범위 포함 필요 |
| 메일·대용량 내보내기 같은 작업이 오래 걸림 | 작업 큐·별도 worker·완료 상태 저장 | 오래 걸리는 작업이 생길 때 검토 |
| 사진·첨부 파일을 영구 보관 | 객체 저장소와 파일 접근 권한 | 파일 업로드 기능이 필요해질 때 검토 |
| 장애 원인·사용자 오류 추적 필요 | 구조화 로그·오류 추적·지표 수집 | 비밀번호·세션 원문 없이 필요한 사건을 기록 |
| 서버나 DB가 실제 부하를 감당하지 못함 | DB 연결 풀·인스턴스/DB 확장 | 동시 사용자 수만 보고 결정하지 않고 측정한 병목에 맞춰 선택 |

인증과 DB 스키마는 기능 테스트만으로 끝내지 않습니다. “다른 사람이 같은 API를 요청하면 어떻게 되는가”, “배포가 실패하면 기존 자료로 돌아갈 수 있는가”까지 확인합니다.

## 7. 7번 과제의 구현 순서 — 초안

1. 6번 실제 제출 커밋과 기존 데이터 기준을 기록합니다.
2. 가입·세션·소유권·이전 정책의 세부 설계를 확정합니다.
3. 테스트 DB에서 사용자와 세션, 비밀번호 처리부터 구현합니다.
4. 모든 앱 API에 인증과 소유권 검사를 적용합니다.
5. 로그인·가입·로그아웃·비밀번호 변경 화면을 연결합니다.
6. 기존 자료 이전과 계정 두 개의 양방향 거절 검사를 수행합니다.
7. 최종 배포에서 로그인 없는 접근·로그아웃 후 재요청·다른 사람 자료 접근을 검증합니다.
8. 고정한 질문·지표로 실제 5일 사용하고, 2일차 후~3일차 전에 규칙을 바꿉니다.
9. 기록·계산·내보내기·설명서를 대조해 제출합니다.

각 단계의 실제 결과는 WORK_LOG_v2.md에 기록합니다. 테스트용 자료와 실제 본인 활동 기록을 구분합니다.

## 8. 구현 후 확인할 핵심 동작

- 가입·로그인·로그아웃과 중복 아이디 거절, 없는 아이디/틀린 비밀번호의 같은 실패 문구.
- 로그인하지 않고 자료 화면 주소를 열면 로그인 화면 표시. API 직접 요청은 인증 오류.
- 같은 비밀번호로 만든 두 계정의 저장 해시는 서로 다름. 원문은 응답·로그·배포 파일·Git 이력에 없음.
- 로그인 중 성공한 요청과 로그아웃 후 같은 인증값을 쓴 거절 요청을 같은 주소·방식으로 비교.
- 비밀번호 변경 후 이전 인증값 거절, 세션 만료 시각과 실제 거절 확인.
- A→B, B→A 자료 읽기·수정·삭제 거절. 거절 전후 자료의 값·건수 불변.
- URL·헤더·본문의 사용자 ID를 바꿔도 자신의 자료만 반환. 목록·집계·내보내기에도 다른 사람 자료 없음.
- 제출용 기록에서는 세션·토큰·비밀번호·비밀키 원문을 가림.

## 9. 실제 5일 사용과 계획 규칙 변경

아직 시작하지 않았습니다. 구현 검증용 날짜를 실제 사용한 날짜로 기록하거나, 나중에 5일치를 실제 활동인 것처럼 만들어 넣지 않습니다.

예시 질문은 “할 일을 더 작게 나누면 하루 실제 집중 시간이 늘어나는가?”처럼 쓸 수 있습니다. 이는 설명용 예시이며 사용자가 선택한 질문이나 결과가 아닙니다.

서울 날짜로 서로 다른 실제 날짜 5일을 기록합니다. 1~2일차의 실제 기록 후, 3일차 기록 전에 계획 규칙 하나를 변경합니다. 변경 시각·이유와 변경 전후 규칙을 남기고, 전후 비교에는 같은 지표·단위·계산 규칙을 사용합니다. 화면의 합계·평균은 원자료를 손으로 계산한 결과와 대조합니다.

## 10. 최종 인증 구현 설명서의 여섯 항목

최종 설명서는 다음 구성을 사용하되, 아직 확인하지 않은 일을 완료로 적지 않습니다.

1. **무엇으로 붙였나:** 인증 구성·라이브러리 이름과 실제 버전.
2. **왜 골랐나:** 선택 이유와 검토했지만 선택하지 않은 다른 방법.
3. **어디를 어떻게 고쳤나:** 파일·함수·DB 구조와 각 역할.
4. **안 열리는 것을 확인한 기록:** 성공/거절 요청 쌍, 양방향 소유권 검사, 세션 무효화와 근거 코드 위치.
5. **AI와 나:** 맡긴 일·본인 판단·따르지 않은 제안과 이유.
6. **아직 못 막은 것:** 실제 미해결 사항과 그 영향. 이 항목을 비워 두지 않습니다.

기존 앱 실행 방법은 [README.md](README.md)를 따릅니다. 인증 코드 구현 후 필요한 환경 설정·사용 방법·실제 검증 명령을 이 문서에 추가합니다.
