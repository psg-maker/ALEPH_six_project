## 3. 구현한 인증 구조

### 선택한 방향과 이유

**기존 FastAPI에 아이디·비밀번호 가입과 DB 세션 인증을 구현하고, 비밀번호 처리는 `pwdlib`의 Argon2 지원에 맡겼습니다.** 사용자의 이해 난도를 낮춰 달라는 요청에 맞춰 Codex가 제안했고, 이후 사용자가 직접 코드를 작성하며 단계별로 확인한 구성입니다.

- 아이디로 가입하므로 처음부터 이메일 발송·이메일 인증 서비스를 연결할 필요가 없습니다.
- 지금 쓰는 FastAPI·SQLAlchemy·Neon 구조를 유지합니다.
- 로그인 상태를 DB에서 확인하므로 로그아웃 때 어떤 값을 끊는지 설명하기 쉽습니다.
- 비밀번호 해시 알고리즘과 salt 처리는 라이브러리를 사용합니다. FastAPI 공식 안내도 `pwdlib`과 Argon2 사용 예제를 제공합니다. [공식 안내](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/)

인증 방식의 정확한 표기는 **“가입·세션 흐름 직접 구현 + 비밀번호 해시 라이브러리 사용”**입니다. 인증 전체를 외부 서비스나 완성된 인증 라이브러리에 맡긴 것으로 설명하지 않습니다. 의존성에는 `pwdlib[argon2]==0.3.1`을 기록했습니다.

| 비교한 방법 | 이번에 우선 선택하지 않은 이유 |
| --- | --- |
| 외부 인증 서비스 | 외부 계정·설정과 자료 소유권 연결까지 한 번에 배워야 함 |
| JWT를 발급하고 브라우저에서만 삭제 | 서버가 이전 값을 거절하게 만드는 별도 폐기 설계가 필요함 |
| 비밀번호 해시를 직접 제작 | 검증된 구현을 사용하고 앱의 흐름과 소유권 검사에 집중하기로 함 |

JWT도 서버에서 폐기 여부를 검사하도록 설계할 수 있습니다. 이번 선택은 가능한 방법 중 현재 앱과 학습 목적에 맞춘 것입니다.

### 용어를 앱 동작으로 이해하기

| 용어 | 이 앱에서 뜻하는 것 |
| --- | --- |
| 인증 | 지금 요청한 사람이 누구인지 확인 |
| 인가 | 그 사람이 요청한 자료를 다뤄도 되는지 확인 |
| 비밀번호 해시 | 비밀번호 원문 대신 저장하는 검사용 값 |
| salt | 같은 비밀번호도 서로 다른 해시가 되도록 사용하는 무작위 값. 라이브러리가 처리 |
| 세션 | 로그인 후 서버가 보관하는 유효기간이 있는 로그인 기록 |
| 쿠키 | 브라우저가 같은 서버에 요청할 때 함께 보내는 작은 값 |
| 소유자 ID | 자료가 어느 사용자에게 속하는지 나타내는 DB 값 |

### 제안 구조

```text
브라우저의 로그인 화면
    │ 아이디·비밀번호 전송(배포 환경은 HTTPS)
    ▼
FastAPI ── pwdlib로 비밀번호 확인
    │ 성공하면 무작위 세션 값 발급
    ├─ 브라우저: HttpOnly 쿠키에 세션 값 보관
    └─ DB: 세션 값의 해시·사용자 ID·만료 시각 보관

이후 자료 요청
    → 서버가 쿠키 값의 해시로 세션 조회
    → 만료·폐기 여부 확인
    → 사용자 ID 확인
    → 그 사용자가 소유한 자료만 조회·변경
```

서버 메모리의 Python 사전 대신 DB에 세션을 둡니다. 요청을 처리하는 서버 인스턴스가 달라져도 같은 로그인 상태를 확인할 수 있도록 하기 위한 설계입니다.

### 요청별 처리 순서

**가입**

1. 아이디와 비밀번호의 입력 형식을 검사합니다.
2. 아이디를 정한 규칙으로 정규화합니다. 중복은 서버 검사뿐 아니라 DB 고유 조건으로도 막습니다.
3. 라이브러리가 만든 비밀번호 해시만 저장합니다. 원문은 로그·응답·문서에 남기지 않습니다.
4. 중복 아이디에는 정해진 오류를 반환합니다.

**로그인**

1. 아이디로 사용자를 찾고 라이브러리로 비밀번호를 검사합니다.
2. 없는 아이디와 틀린 비밀번호는 같은 실패 문구를 반환합니다.
3. 성공하면 추측하기 어려운 세션 값을 새로 만듭니다.
4. DB에 세션 값의 해시와 만료 시각을 저장하고, 브라우저에 쿠키를 설정합니다.

**자료 요청**

1. 세션이 없거나 만료·폐기됐으면 API는 401로 거절합니다.
2. 로그인한 사용자 ID를 서버가 결정합니다. 요청 본문·URL·헤더의 다른 사용자 ID를 신뢰하지 않습니다.
3. 자료 ID와 소유자 조건을 함께 검사합니다.
4. 개별 자료 접근에서 다른 사람 자료와 없는 자료는 동일하게 404로 처리합니다. 목록에 상대 계획 ID를 필터로 지정한 경우에는 상대 자료가 없는 빈 목록을 반환합니다.
5. 소유권 확인 후에만 변경하고, 실패하면 트랜잭션 전체를 취소합니다.

**로그아웃·비밀번호 변경**

- 로그아웃은 현재 세션을 DB에서 폐기하고 쿠키도 지웁니다.
- 메인 상단의 비밀번호 변경 화면에서 현재 비밀번호와 새 비밀번호·확인을 입력합니다. API는 현재 비밀번호 확인 후 새 해시를 저장하고, 해당 사용자의 기존 세션을 모두 폐기합니다. 성공하면 로그인 화면으로 이동해 다시 로그인합니다.
- 이전 쿠키를 보관했다가 다시 보내도 서버가 거절해야 합니다. OWASP는 로그아웃과 만료 때 서버 측 세션 무효화를 요구합니다.
[세션 관리 안내](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

쿠키에는 `HttpOnly`, `SameSite=Lax`, `Path=/`, 12시간 `Max-Age`를 사용하고 요청이 HTTPS로 인식되면 `Secure`를 설정합니다. `SameSite`만으로 모든 변경 요청을 보호했다고 보지 않으며 자료 변경 API 전반의 CSRF 점검은 남아 있습니다.
[쿠키·세션 설정](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html),
[CSRF 방어](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

아이디는 앞뒤 공백을 제거하며 대소문자는 구분하고, 길이는 1~50자입니다. 비밀번호는 입력 그대로 15~128자를 받습니다. 세션 만료는 12시간의 고정 만료이며, 자료 API가 401을 반환하면 화면은 `/login`으로 이동합니다. 아무 요청도 없는 화면을 만료 시각에 맞춰 즉시 전환하는 타이머는 없습니다. 로그인·로그아웃·비밀번호 변경·계정 삭제에는 Origin 검사가 있으나 모든 자료 변경 API에 동일한 검사를 연결한 것은 아니므로, CSRF 방어 전체 완료로 해석하지 않습니다. 운영 프록시의 HTTPS 인식과 쿠키 속성은 배포 시 확인해야 합니다.

**계정 삭제와 자료 처리**

하단의 계정 삭제 확인창에서 현재 비밀번호와 정확한 `계정 삭제` 문구를 입력하면 `DELETE /auth/account`를 요청합니다. 서버는 로그인한 계정만 대상으로 하며, 본인의 링크·실행 기록 → 할 일 → 계획 수정 이력·회고 → 계획 → 일일 메모 → 인증 세션 → 계정 순으로 하나의 트랜잭션에서 삭제합니다. 실패하면 전체를 롤백하고 다른 사용자의 자료는 삭제하지 않습니다.

성공하면 쿠키를 지우고 로그인 화면으로 이동합니다. 삭제 후 앱에서 복구할 수 없으며, 기존 백업 사본은 이 작업으로 삭제되지 않는다는 점을 확인창에 안내합니다. DB 연쇄 삭제 대신 서버에서 참조 관계에 맞춰 순서대로 삭제하는 방식을 사용자가 선택했습니다.

## 4. DB에서 사용자별 자료를 구분하는 방법

| 대상 | 변경 방향 |
| --- | --- |
| User | 사용자 ID·정규화한 고유 아이디·비밀번호 해시·생성 시각 |
| AuthSession | 사용자 참조·고유 세션 해시·만료/폐기 시각 |
| Plan | user_id 정의·로컬 DB 적용·기존 계획의 지정 계정 연결 완료. 운영 DB 적용은 남음 |
| Task | 연결된 Plan의 소유자를 통해 접근 검사 |
| Execution·TaskLink | 연결된 Task → Plan의 소유자를 통해 접근 검사 |
| PlanVersion·Review | 연결된 Plan의 소유자를 통해 접근 검사 |
| Review.next_plan_id | 현재 계획과 연결 대상 계획 모두 같은 사용자의 소유인지 검사 |
| DailyNote | user_id와 `(사용자 ID, 날짜)` 고유 조건을 로컬 DB에 적용. 저장·조회 모두 사용자+날짜 조건 사용 |

예를 들어 사용자 A와 B가 같은 날짜에 일일 메모를 작성해도 각각 저장돼야 합니다. 현재 날짜만 고유한 구조를 그대로 두면 다중 사용자 기능과 맞지 않습니다.

현재 모델과 로컬 DB의 메모 고유 조건은 사용자·날짜 조합입니다. 같은 사용자·날짜에 새 행을 추가하는 것은 거절하고 기존 행의 content 수정은 허용합니다. 서로 다른 사용자의 같은 날짜 저장, 기존 메모 수정 시 ID 유지와 다른 사용자 자료 보존을 직접 SQL 및 로컬 API에서 확인했습니다. `Plan.user_id`, `DailyNote.user_id`는 이전 단계의 nullable 정의가 남아 있어 NULL을 포함한 고유 조건만으로 소유권 필수 입력을 보장하지는 않습니다. API에서 사용자 ID를 지정하고 최종 DB 제약 정리는 별도로 수행해야 합니다.

목록·검색·필터·집계·근거 목록·내보내기도 사용자 범위를 적용합니다. 개별 ID 조회만 막고 목록에 다른 사람 자료가 섞이는 경우도 검사합니다.

내보내기에는 사용자 자신의 앱 자료만 담고 비밀번호 해시·세션 해시·쿠키 값은 포함하지 않습니다. 7번용 DB 계약을 작성할 때 기존 6번 계약의 설명과 구분합니다.

## 5. 기존 6번 자료를 안전하게 이전하는 순서

```text
기존 DB와 제출 커밋 확인
→ 백업과 기존 ID·값·관계 점검
→ 테스트 DB에서 사용자·소유권 스키마 변경 리허설
→ 자료를 받을 본인 계정 지정
→ 지정한 계정에 기존 자료 연결
→ 이전 전후 ID·값·관계·건수 대조
→ 인증을 포함한 앱과 DB 변경을 맞춰 배포
→ 본인 계정 조회 및 다른 계정 접근 거절 확인
```

“처음 가입한 사람”에게 기존 자료를 자동으로 주지 않습니다. 공개 가입 순서가 자료 소유자를 결정해서는 안 됩니다. 로컬에서는 사용자가 지정한 계정의 ID와 아이디를 조회·대조한 후 소유자가 NULL인 기존 계획 2건·메모 2건만 연결했습니다. 운영 DB의 소유자는 운영 계정과 자료를 확인한 뒤 별도로 지정해야 합니다.

기존 ID·실행 내용·계획 수정 이력을 보존합니다. 기존 DB에 `create_all()`만 실행해도 컬럼·고유 조건이 바뀌는 것은 아니므로, 별도 마이그레이션이 필요합니다. 배포 순서와 실패 시 복구 방법까지 테스트한 뒤 적용합니다.

`scripts/migrate_ownership_sqlite.py`는 현재 로컬 `planner.db`를 대상으로 하는 SQLite용 학습 스크립트입니다. 테스트 복사본에서 변경 성공·재실행 시 생략·실패 후 구조와 자료 롤백을 확인한 뒤 로컬에 적용했습니다. 실행 전 백업은 수동으로 생성해야 하며 스크립트가 자동 생성하지 않습니다. PostgreSQL에 그대로 실행하거나 운영 이전 도구가 완성됐다고 간주하지 않습니다.

## 6. 개인 프로그램에서 다중 사용자 서비스로 발전시키는 판단 순서

먼저 다음 질문을 차례로 확인합니다. 서비스가 커졌다는 이유만으로 모든 기술을 한꺼번에 추가하지 않습니다.

```text
1. 내 PC 밖에서도 써야 하나?
   → 서버에 배포하고 영구 저장 위치를 정한다.
2. 여러 사람이 서로 다른 자료를 쓰나?
   → 사용자·인증·자료 소유권·접근 제한을 추가한다.
3. DB 구조를 바꾸면서 기존 자료를 유지해야 하나?
   → 백업·마이그레이션·복구 절차를 둔다.
4. 무엇이 느리거나 실패하는지 측정했나?
   → 로그·응답 시간·DB 쿼리와 연결 수부터 확인한다.
5. 확인한 원인은 무엇인가?
   → 원인에 맞는 인덱스·캐시·작업 큐·서버 확장을 선택한다.
6. 바꾼 뒤 개선됐고 사용자 자료가 분리되는가?
   → 같은 기준으로 다시 측정하고 권한 검사도 반복한다.
```

| 상황·문제 | 보통 고려하는 구성 | 이 프로젝트에서의 판단 |
| --- | --- | --- |
| 혼자 로컬에서 기능을 익힘 | Python·FastAPI·SQLite | 6번 로컬 개발 구성으로 사용 중 |
| 외부 기기에서도 접속·저장 | 호스팅·HTTPS·영구 DB | Vercel·Neon 사용 중 |
| 여러 사용자가 각자 자료 사용 | User·비밀번호 라이브러리·세션·소유권 검사 | 로컬 API와 화면에 적용·검증, 운영 적용은 남음 |
| 기존 자료를 유지한 DB 변경 | SQL 마이그레이션 스크립트 또는 Alembic | SQLite용 스크립트와 복사본 리허설 수행. 운영 PostgreSQL 절차는 별도 준비 |
| 자주 조회하는 목록이 느림 | 쿼리 개선·소유자/날짜 인덱스·페이지 나누기 | 실제 쿼리와 응답 시간을 확인한 뒤 적용 |
| 같은 계산을 반복해 DB 부담 증가 | 캐시. 공유 캐시가 필요하면 Redis 등 검토 | 현재 필수 도입 대상 아님. 캐시 키에도 사용자 범위 포함 필요 |
| 메일·대용량 내보내기 같은 작업이 오래 걸림 | 작업 큐·별도 worker·완료 상태 저장 | 오래 걸리는 작업이 생길 때 검토 |
| 사진·첨부 파일을 영구 보관 | 객체 저장소와 파일 접근 권한 | 파일 업로드 기능이 필요해질 때 검토 |
| 장애 원인·사용자 오류 추적 필요 | 구조화 로그·오류 추적·지표 수집 | 비밀번호·세션 원문 없이 필요한 사건을 기록 |
| 서버나 DB가 실제 부하를 감당하지 못함 | DB 연결 풀·인스턴스/DB 확장 | 동시 사용자 수만 보고 결정하지 않고 측정한 병목에 맞춰 선택 |

인증과 DB 스키마는 기능 테스트만으로 끝내지 않습니다. “다른 사람이 같은 API를 요청하면 어떻게 되는가”, “배포가 실패하면 기존 자료로 돌아갈 수 있는가”까지 확인합니다.

## 10. 최종 인증 구현 설명서의 여섯 항목

1. **무엇으로 붙였나:** 인증 구성·라이브러리 이름과 실제 버전.
2. **왜 골랐나:** 선택 이유와 검토했지만 선택하지 않은 다른 방법.
3. **어디를 어떻게 고쳤나:** 파일·함수·DB 구조와 각 역할.
4. **안 열리는 것을 확인한 기록:** 성공/거절 요청 쌍, 양방향 소유권 검사, 세션 무효화와 근거 코드 위치.
5. **AI와 나:** 맡긴 일·본인 판단·따르지 않은 제안과 이유.
6. **아직 못 막은 것:** 실제 미해결 사항과 그 영향. 이 항목을 비워 두지 않습니다.

## 11. 로컬 실행과 인증 화면 사용

프로젝트 폴더의 Git Bash에서 실행합니다. `venv`가 준비된 기존 개발 환경 기준입니다.

```bash
DATABASE_URL='sqlite:///./planner.db' ./venv/Scripts/python.exe -m uvicorn app.main:app --reload
```

DB 경로는 `planner.db`입니다. `.planner.db`는 앞에 점이 있는 별도 파일입니다. 실제로 다른 파일을 사용해 계정·계획이 다르게 보였던 일이 있어, 위 명령처럼 서버 실행에 연결 대상을 명시합니다. 비밀번호·외부 DB 연결 주소는 문서에 공유하지 않습니다.

- `http://127.0.0.1:8000/`: 비로그인이면 `/login`으로 303 이동, 로그인 상태면 자신의 앱 화면 표시.
- `/login`: 기본 로그인 모드, 같은 화면에서 회원가입 전환. 가입 성공 후 아이디를 유지하고 비밀번호를 비운 뒤 로그인 모드로 복귀하며 자동 로그인하지 않음.
- 이미 로그인한 사용자가 `/login`을 열면 `/`로 이동.
- 메인 상단의 계정명과 로그아웃 버튼: 로그아웃 API 성공 후 로그인 화면으로 이동. 실패하면 오류를 표시하고 재시도 가능.
- 자료 API의 401은 `session.js` 공통 함수가 처리. 계획·메모·회고·돌아보기 스크립트는 JSON 처리 전에 세션 응답을 검사.
- 메인 상단의 비밀번호 변경: 현재 비밀번호·새 비밀번호·확인 입력 후 변경. 성공하면 다시 로그인하며 이전 비밀번호는 거절.
- 하단의 계정 삭제: 현재 비밀번호와 `계정 삭제` 문구를 확인한 후 계정과 본인 자료 삭제. 처리 중 중복 제출을 막고 성공 시 로그인 화면으로 이동. 검증에는 새로 만든 삭제 검증용 계정을 사용.
- 비밀번호 찾기는 아직 미구현. `/docs`도 실제 API를 실행하므로 비밀번호 변경·삭제 요청은 연결된 DB에 반영됨.

로그인 페이지에는 `auth.css`, `auth.js`, 메인에는 `session.js`, `password.js`, `account-delete.js`와 기존 화면별 스크립트를 사용합니다. `session.js`는 자료 스크립트보다 먼저 한 번만 로드합니다. 입력 내용과 오류는 `textContent` 또는 템플릿 자동 이스케이프로 표시하고 비밀번호·세션 값은 localStorage에 저장하지 않습니다.
