# ALEPH — 내 계획과 실제를 담는 앱

FastAPI · SQLAlchemy로 만든 Plan → Do → See 기록 앱입니다. 화면과 API는 Vercel에 배포한 하나의 FastAPI 앱에서 제공하며, 배포 데이터는 Neon PostgreSQL에 저장합니다. 로컬 개발에서는 기본적으로 SQLite를 사용합니다. 로그인은 없으며, 링크를 아는 사람이 자료를 조회·변경·삭제할 수 있습니다.

- Vercel 앱 배포 및 Neon 연결 완료. 배포 앱에서 이전한 기록 조회와 시크릿 창 공개 접근을 사용자가 확인했습니다.

- 최종 앱 URL과 고정 commit URL은 제출 시 기록합니다. 배포 앱의 새 기록 저장·재배포 후 유지, 집계 근거 및 서울 날짜 기준의 최종 확인은 [제출 점검표](SUBMISSION_CHECKLIST.md)에서 관리합니다.
FastAPI · SQLAlchemy · SQLite로 만든 Plan → Do → See 기록 앱입니다. 화면과 API는 같은 FastAPI 서버에서 제공합니다. 로그인은 없으며, 공개 배포하면 링크를 아는 사람이 자료를 조회·변경할 수 있습니다.

## 실행 — Windows Git Bash

현재 개발 환경은 Python 3.13입니다. 프로젝트 루트에서 실행합니다.

```bash
# 가상환경이 없을 때만 생성
python -m venv venv

./venv/Scripts/python.exe -m pip install -r requirements.txt
./venv/Scripts/python.exe -m uvicorn app.main:app --reload
```

- 앱: http://127.0.0.1:8000/
- API 확인: http://127.0.0.1:8000/docs
- 종료: `Ctrl+C`

8000 포트를 사용할 수 없다면 기존 서버를 종료하거나 `--port 8001`을 붙이고 접속 주소도 8001로 바꿉니다. HTML 파일을 직접 열거나 Live Server로 실행하지 않습니다.

Linux에서는 별도로 만든 가상환경의 `./venv/bin/python`을 사용합니다. Windows 가상환경을 복사해 사용하지 않습니다.

## 데이터 보관

앱은 환경변수 `DATABASE_URL`로 사용할 DB를 선택합니다.

| 환경 | DB | 저장 위치 |
| --- | --- | --- |
| 로컬 기본값 — 환경변수 없음 | SQLite | 서버를 실행한 현재 폴더의 `planner.db` |
| Vercel 배포 — 환경변수 설정 | Neon PostgreSQL | Neon 프로젝트의 해당 브랜치·데이터베이스 |

로컬에서는 항상 프로젝트 루트에서 실행하세요. 다른 폴더에서 실행하면 다른 SQLite DB가 생길 수 있습니다. 기존 DB는 삭제하거나 초기화하지 않습니다. 로컬 SQLite와 배포 Neon은 별도 DB이며 자동 동기화되지 않습니다. 로컬에도 같은 Neon 연결 주소를 설정하면 공개 앱과 동일한 데이터를 조회·변경하게 됩니다.

- 소스만 clone하면 개인 데이터가 자동 복원되지 않습니다. DB·백업·환경변수는 Git에서 제외합니다.
- 로컬 SQLite는 실행 중인 앱을 종료한 뒤 DB 파일을 별도 위치에 복사해 백업합니다. 이 파일은 Neon의 이후 변경사항을 포함하지 않습니다. `전체 기록 내보내기`는 현재 앱이 연결한 DB의 7개 테이블을 JSON으로 다운로드하지만 현재 JSON 가져오기 기능은 없습니다.
- 새 DB는 서버 시작 시 테이블이 생성됩니다. 기존 DB의 컬럼 변경은 자동 적용되지 않습니다.
- 오래된 로컬 SQLite DB에서 `executions.blocked_reason`이 없다는 오류가 나면 삭제 대신 백업 후 스키마를 확인해야 합니다. 필요한 변경은 `ALTER TABLE executions ADD COLUMN blocked_reason TEXT`이며, 이미 컬럼이 있는 DB에 다시 실행하지 않습니다.

테이블·컬럼·외래키·NULL·고유 조건과 동작 규칙은 [DB 계약](contracts/pds-schema-v2.json)에 기록했습니다. 현재 계약 파일의 DB 엔진·경로·시각 설명은 이전 SQLite 구성 기준으로, Neon 배포와 아래 서울 시간 정책에 맞춘 갱신이 남아 있습니다. 계약 파일 자체는 DB 마이그레이션을 실행하지 않습니다.

## Vercel·Neon 설정

Vercel 프로젝트의 환경변수 `DATABASE_URL`에 Neon 연결 주소를 등록합니다. 현재 설치한 드라이버에 맞춰 주소 시작 부분은 `postgresql+psycopg2://`로 지정하고, Neon이 제공한 SSL 연결 옵션을 유지합니다. 실제 연결 주소와 비밀번호는 소스·README·Git에 넣지 않습니다. 환경변수를 변경하면 재배포해야 반영됩니다.

Vercel은 `app/main.py`의 FastAPI 앱을 실행합니다. 화면과 API를 별도 프로젝트로 분리하지 않습니다. 로컬의 `planner.db` 파일을 Vercel의 영구 저장소로 사용하지 않습니다.

기존 자료 이전에는 [이전 스크립트](scripts/migrate_to_neon.py)를 사용했습니다. 스크립트의 환경변수 `NEON_DATABASE_URL`은 이전 대상 지정용으로, 앱의 `DATABASE_URL`과 구분합니다. 기본 실행은 원본 읽기 전용 미리보기이고 `--apply`를 지정하면 빈 대상 DB에 이전합니다. 기존 대상 테이블이 있으면 중단하며 ID·연결 관계·전체 값을 검증합니다. 이 프로젝트의 Neon 이전은 완료했으므로 다시 실행할 필요가 없습니다.

## 사용 및 확인 — 세 단계

1. `새 계획`을 만든 뒤 연결된 할 일을 추가합니다. 계획은 수정 후 `수정 이력`에서 이전 내용을 확인할 수 있습니다.
2. 할 일의 `실행 기록`에서 실제 시간을 분 단위로 직접 입력하고 완료를 체크합니다. 예상 시간과 실제 시간은 별도로 저장되며 스톱워치는 없습니다.

3. `돌아보기`에서 계획을 선택하고 집계 숫자를 눌러 근거를 확인합니다. 회고의 고칠 점을 저장한 뒤 다음 계획에 반영할 수 있습니다.
`돌아보기`에서 계획을 선택하고, 필요하면 예정일 시작·종료를 입력해 `기간 적용`을 누릅니다. 집계 숫자를 눌러 같은 범위의 근거를 확인합니다. 회고의 고칠 점을 저장한 뒤 다음 계획에 반영할 수 있습니다.

통과 확인: 새로고침과 서버 재시작 뒤 자료가 남고, 집계와 근거 기록이 일치하며, 반복 완료로 실행 기록이 추가되지 않습니다. 날짜별 메모도 저장할 수 있습니다. 저장 전 메모 초안은 현재 페이지 안에서만 유지됩니다.

안 될 때: 서버 실행 로그와 접속 포트를 확인합니다. 목록 조회 오류는 화면의 재시도를 사용하고, DB 컬럼 오류는 위 데이터 보관 항목을 확인합니다. 같은 값은 화면에서 ID 오름차순으로 정렬하며 미입력은 항상 마지막입니다.

## 휴대폰 확인

배포 앱은 휴대폰 브라우저에서 공개 URL로 확인합니다. 로컬 앱을 휴대폰에서 확인하려면 PC와 휴대폰을 같은 Wi-Fi에 연결합니다.
PC와 휴대폰을 같은 Wi-Fi에 연결합니다.

```bash
./venv/Scripts/python.exe -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

다른 터미널에서 `ipconfig`로 사용 중인 네트워크의 IPv4 주소를 확인하고 휴대폰에서 `http://PC의IPv4주소:8000/`을 엽니다. 신뢰하는 사설 네트워크의 방화벽 허용이 필요할 수 있습니다. 이 주소는 제출용 공개 주소가 아닙니다. 확인 후 서버를 종료합니다.

## 테스트

개인 DB와 분리한 메모리 DB와 이전 검사용 임시 SQLite DB를 사용합니다. 이전 테스트는 실제 Neon에 연결하지 않습니다.

```bash
./venv/Scripts/python.exe -B -m unittest discover -s tests -v
node --check app/static/planner.js
```

DOM/API 연동 테스트는 [테스트 설명](tests/README.md)을 따릅니다. DOM 테스트는 실제 브라우저 배치·키보드·휴대폰 조작을 대신하지 않습니다.

## 배포 및 제출 상태

Vercel+Neon 배포와 기존 기록 조회, C61 공개 접근 확인을 마쳤습니다. GitHub는 소스 보관에 사용하며, GitHub Pages로 Python 앱을 실행하는 구성은 아닙니다. 공개 DB는 로그인 없이 변경할 수 있으므로 로컬 백업과 배포 이후 자료를 구분해 보관합니다.

현재 돌아보기는 선택한 계획의 전체 기록 기준입니다. 임의 날짜 범위 집계는 없습니다. 최종 공개 URL, 고정 commit URL, 공개 가능한 실제 기록과 AI 활용 총평 등은 [제출 점검표](SUBMISSION_CHECKLIST.md)에서 관리합니다. 채팅 버전의 빈 제목 자동 생성은 후속 계획이며 현재 기능이 아닙니다.
공개 앱 배포는 아직 완료되지 않았습니다. GitHub Pages는 Python 서버를 실행하지 않으므로 이 앱 전체를 동작시키는 배포 환경이 아닙니다. FastAPI 실행 환경과 영구 DB 저장 공간이 필요합니다.

현재 날짜와 생성 시각은 서버 로컬 시간 기준이며 명시적인 한국 시간 변환은 없습니다. 실행 시각은 시간대 없는 입력값을 그대로 저장합니다. 배포 전에 DB 경로·영구 저장소와 시간대 정책을 확정해야 합니다.

돌아보기는 기본적으로 선택한 계획의 전체 기록을 집계합니다. 기간을 적용하면 **예정일이 시작일~종료일에 포함되는 할 일**을 대상으로 하며 양쪽 경계를 포함합니다. 한쪽 날짜만 입력해도 되고, `전체 기간`으로 초기화할 수 있습니다. 대상 할 일에 연결된 실행 기록은 실행 날짜와 무관하게 모두 포함합니다. 완료는 현재 상태, 지연은 오늘 기준이며 과거 시점의 상태를 복원하는 기능은 아닙니다. 입력 중인 날짜는 `기간 적용`을 누르기 전에는 집계에 반영되지 않습니다. 이 기능은 로컬 구현·테스트 완료 상태이며 배포 후 확인이 필요합니다.

API에서는 `GET /tasks`, `GET /plans/{plan_id}/summary`, `GET /plans/{plan_id}/executions`에 선택 쿼리 `start_date=YYYY-MM-DD&end_date=YYYY-MM-DD`를 사용합니다. 날짜를 생략하면 기존 전체 조회가 유지되며 잘못된 날짜나 역전된 기간은 422로 거부합니다.

최종 공개 URL, 고정 commit URL, 공개 가능한 실제 기록과 AI 활용 총평 등은 [제출 점검표](SUBMISSION_CHECKLIST.md)에서 관리합니다. 채팅 버전의 빈 제목 자동 생성은 후속 계획이며 현재 기능이 아닙니다.
