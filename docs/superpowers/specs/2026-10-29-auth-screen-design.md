# 로그인·회원가입 화면 연결

## 목적

7번 과제의 인증 API를 일반 화면에 연결한다. 비로그인 사용자는 로그인 화면부터 보고, 로그인 후 자신의 계획·할 일·메모 화면에 진입한다. 사용자가 직접 작성하며 학습할 수 있도록 작은 단계로 진행한다.

## 선택한 접근

- 사용자가 선택한 방식: 한 화면에서 로그인과 회원가입을 전환한다.
- 비교한 대안: 별도 페이지로 분리하면 역할은 명확하지만 화면 파일과 이동 경로가 늘어난다.
- 기존 FastAPI·Jinja2·일반 JavaScript와 세션 쿠키를 유지한다. 새 인증 라이브러리는 도입하지 않는다.

## 제안하는 동작

1. 비로그인 상태로 `/` 접근 시 `/login`으로 이동한다. `/login`은 로그인·회원가입 전환 화면이다.
2. 화면의 기본 모드는 로그인이다. 회원가입은 같은 화면에서 전환한다.
3. 로그인은 기존 `POST /auth/login`을 호출한다. 성공하면 서버가 발급한 HttpOnly 쿠키로 인증하고 `/`로 이동한다.
4. 회원가입은 기존 `POST /auth/register`를 호출한다. 성공하면 같은 화면의 로그인 모드로 돌아가며 아이디를 채우고 비밀번호는 비운다. 자동 로그인은 하지 않는다.
5. 유효한 세션으로 `/login`에 접근하면 `/`로 이동한다. 앱 화면에 사용자명과 로그아웃 버튼을 표시한다.
6. 로그아웃은 기존 API의 성공 응답을 확인한 뒤 로그인 화면으로 이동한다. 요청 실패 시 완료된 것처럼 표시하지 않는다.
7. 로그인 만료로 자료 API가 401을 반환하면 로그인 화면으로 이동한다. API 자체는 기존대로 JSON 401을 반환하며 HTML로 바꾸지 않는다.

## 화면과 입력

- 기존 ALEPH 색상·글꼴에 맞춘 간단한 중앙 폼을 제안한다.
- 아이디·비밀번호 라벨, 비밀번호 길이 안내(15~128자), 처리 중 버튼 잠금, 입력 오류 표시를 제공한다.
- 로그인/회원가입에 맞는 autocomplete을 사용한다. 비밀번호·세션 토큰은 localStorage나 로그에 저장하지 않는다.
- 사용자명과 오류 문구는 textContent 또는 Jinja2 자동 이스케이프로 출력한다.
- 기존의 '로그인 없이 누구나 볼 수 있다'는 안내는 현재 인증 방식에 맞게 교체한다.

## 작업 범위와 검증

- 화면 템플릿·정적 파일·HTML 진입 경로를 연결한다. 사용자별 자료 API의 권한 검사는 유지한다.
- 비밀번호 찾기, 소셜 로그인, 계정 삭제, 운영 DB 마이그레이션·배포는 이번 범위에서 제외한다.
- 첫 단계는 로그인 화면과 `/` 진입 검사다. 이후 회원가입·로그아웃·만료 처리를 연결한다.
- 임시 DB에서 HTML 이동 경로와 기존 인증 테스트를 확인하고, 브라우저에서 로그인·회원가입·로그아웃을 확인한다.
- 로컬 DB의 기존 계정과 자료는 그대로 보존한다. commit·push·배포는 별도 진행한다.

## 상태

방식 선택 완료. 위 세부 동작에 대한 사용자 검토 후 구현한다.
